# 設計原則

這份文件記錄幾個「刻意這樣做」的決定，避免日後改版時走回頭路。

---

## 1. 不是所有項目都應該變成遊戲

35 個項目之中，有 **11 個仍然是「實作任務」**（露營、服務、家庭章、歷險挑戰、分享經驗）。
這不是未完成，是刻意保留。

**判斷標準：**

| 類型 | 例子 | 做法 |
|---|---|---|
| 知識 / 判斷 / 次序 / 記憶 | 誓詞、國旗、繩結用途、急救步驟 | ✅ 做成遊戲，手機自己玩得完 |
| 真實世界的體驗與考核 | 露營、長途遠足、社區服務 | ⛔ 保持「實作任務」，由領袖／家長核對 |

**理由：** 如果「考露營章」變成在手機上點幾下就通關，小朋友會覺得假，領袖也會反對。
手機負責「知識與練習」，真實活動負責「體驗與考核」——混合制才有說服力，也符合童軍「做中學」的精神。

**但這不等於「沒有遊戲感」**：實作任務仍然可以有進度條、累積時數、解鎖動畫。
只是**解鎖條件不是答對題目，而是真實做過**。

---

## 2. 過關不等於刁難

- 答錯**不會扣分、不會失敗、不會失去進度**，只會顯示解釋，讓小朋友再揀一次。
- 只有兩種情況會「失敗」：限時搵嘢超時。
- 通關一律給 ⭐ 以上；⭐⭐⭐ 只代表「零錯誤」，是榮譽不是門檻。

**理由：** 使用者是 7–12 歲。這個年齡的遊戲化重點是**回饋頻率**，不是難度曲線。
難度來自「真實世界的挑戰」，不是手機上的操作。

---

## 3. 為什麼不用 React

- 專案的核心是**內容**（35 關題目）和**遊戲規則**（8 種引擎），不是複雜的 UI 狀態。
- 零依賴 → 一個 HTML 檔，WhatsApp 傳得走，十年後瀏覽器還開得開，GitHub Pages 免費放。
- 沒有 build step 也能跑：`index.html` 直接開就是完整功能。

**什麼時候才應該換框架：** 當要做「領袖後台 + 全團 60 人 + 跨裝置同步」時，
那時才用 Vite + React + Supabase 重寫，而且只重寫「資料層與後台」，遊戲引擎可以整段搬過去。

---

## 4. 資料與程式分離

所有中文內容集中在 `js/data.js`，結構固定：

```
STAGES  → 有哪些階段、每個階段有哪些項目（順序 = 關卡 id）
GAMES   → 每個項目對應的遊戲內容
BADGES  → 活動徽章收藏
MISSIONS / CARDS / RANKS / AVATARS → 每日任務、激勵卡、等級、頭像
```

**目的：** 讓不懂程式的人（例如團長）也能改題目，改完跑 `npm run check` 就知道有沒有打錯。

---

## 5. 資料要老實

- 獎章名稱、項目名稱 → 依官方《幼童軍訓練綱要》。
- 遊戲題目、答案、情境 → **本專案自行設計**，不是官方考核材料，已在畫面上標明。
- 正式在團內使用前 → 交團長／區總監審閱。

寧願寫「示範設計」，也不要讓領袖以為這是官方教材。
